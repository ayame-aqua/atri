## 做什么

把执行顺序定为 **P1 → P2-A → P3 → P4 → P7 → P5 → P6**。阶段编号含义不变，只改先后，并一次收口下面这些设计缝。

阶段编号仍是 P1 人设、P2 记忆、P3 语音、P4 Live2D、P5 QQ、P6 微信、P7 桌宠。不重编号，避免交叉引用全乱。

> 后续 v0.12 已重编号为 P5 桌宠 / P6 QQ / P7 微信。本文保留当时决策原文。

## 为什么

本机陪伴是产品主线。旧顺序 `P1→P2→P3→P4→P5→P6→P7` 把 QQ/微信插在桌宠前面，桌宠（README 的核心承诺）要等 IM 做完才开始。

纯 `P1→P3→P2→…`（先语音后记忆）能更快听到声音，但语音聊到的称呼和约定重启即忘。因此 **P2 拆成两截**：

- **P2-A 最小记忆（硬门，挡在 P3 之前）**：称呼、关系、明确「记住」的事实、SQLite 落盘、「忘掉」、简单查看/编辑。
- **P2-B 记忆补强（非阻塞）**：episodes、向量检索、风格库、群导出导入、完整待确认队列。不挡 P3/P4/P7；建议在 P5 前补完。

其它收口：

1. 人设只出 `[[emotion:]]`、P2 又要 JSON，协议冲突 → P1 起统一不可见 `[[atri]]` 尾块，并规定解析失败降级。
2. P5「P4 不阻塞」、P7「P5 建议已通」与总纲「严格 P1→P7」打架 → 总纲写唯一硬依赖表。
3. 个人微信是最大外部风险 → P6 验收前增加合规可行性确认；无稳定路径则实验性适配器，核心不依赖它。
4. 每次改动都打 tag、push、等 CI 过重 → 规则改为阶段交付或用户明确要求发布时才版本化。
5. README 标 MIT 但无 LICENSE 文件 → 补许可证。
6. P1 标题写「网页 / 桌面」但内容不做桌宠 → 标题改为「网页文字聊天与人设」。
7. P1 工程基线偏软 → `pyproject.toml`、锁文件、单元测试、`message_id`、错误码、重复 WS 处理；CI 要跑测试。
