## 1. 本阶段要做成什么样

QQ 已经证明 Channel 模式能用。P6 把微信做成第二条即时通讯皮，体验是：**微信好友对话框**，不是企微应用，也不是公众号客服窗。桌宠已在 P7 完成，不要把看屏接到微信。

她用另行准备的微信号；**只有合规可行性确认通过后**才写登录/收发。确认失败则只保留空壳或 `experimental` 适配器，默认 `enabled: false`。P1–P5 仍然禁止出现微信登录器。

### 1.0 合规可行性确认（硬门，写进 `docs/开发计划/变更/` 或本文件附录）

开工写协议代码之前，必须书面回答：

1. **路径**：官方开放能力 / 已获授权的方案 / 其它你愿意承担风险的方案，选哪一条，依据是什么。
2. **账号**：用哪个号、封号或限制登录时记忆是否仍在本机（必须仍在）。
3. **许可**：是否违反平台 ToS；自用实验能否接受该风险。
4. **维护**：这条接入在 12 个月内有没有可预期的维护方式；作者跑路怎么办。

结论只能是下面之一：

- **通过：** 按 1.1 做正式通道，验收清单全开。
- **不通过：** 适配器标 `experimental`，默认关闭，CI / Core 单测不得 import 其实现细节；总纲架构图里的微信框视为可拆插件。主线验收 **不** 要求好友聊天打通。

不允许「先接上再看会不会封」。

### 1.1 要做（仅「通过」时作为验收项；「不通过」时做可卸载空壳即可）

- `channels/wechat.py` 实现 `Channel`：收文本、发文本、白名单
- `chatId`：`wechat:dm:<id>`（先做私聊你）
- 同一 `MemoryStore`、同一人设
- 策略靠近 **QQ 私聊**：比群积极，比桌宠克制；不要桌宠式主动刷屏
- 接入方式在 **P6 开工时**再定具体网关；对 Core 只暴露 `send_text`（表情有现成能力再加，不阻塞文字验收）

### 1.2 明确不做

- **企业微信**（应用、客服、企微群都不做）
- **公众号 / 服务号**（不是好友聊天）
- 改一套「微信人格」或另训模型
- 本阶段不要求语音、朋友圈、看你的桌面
- 不采集你没有管理权的微信群

## 2. 架构

与 QQ 相同，禁止在适配器里直接调 LLM：

```
微信事件 -> WechatChannel -> Gateway -> Agent -> wechat.send
```

微信 Agent **不要**注册 `see_screen`。表情 MCP 能复用就复用，不能就 P6 只发文字。

---

## 3. 配置草稿

```yaml
channels:
  wechat:
    enabled: false
    allow_private: []       # 只填你的微信标识
    allow_groups: []        # 默认空；P6 验收不依赖群
    allow_all_when_empty: false
    send_delay_ms_min: 800
    send_delay_ms_max: 2500
```

白名单 fail-closed。凭证进 `.env`，与记忆文件分离。

---

## 4. 行为

- 只对白名单私聊走 Agent
- 纯文本；超长按通道上限切开
- 不发 emotion 行
- 非白名单：不回

---

## 5. 实现顺序

1. 选定个人微信接入方式，白名单私聊 ping/pong
2. 接 Gateway + 记忆
3. 限频、切段、错误提示
4. 验收与网页 / QQ 记忆一致

## 6. 验收

- [ ] 合规可行性确认有书面结论（通过或不通过）
- [ ] **通过时：** 微信好友聊天能来回，人设正确
- [ ] **通过时：** 网页或 QQ 记住的称呼，微信侧仍知道
- [ ] **通过时：** 非白名单不回复
- [ ] **不通过时：** `channels.wechat.enabled` 默认 false；关掉后网页/语音/桌宠/QQ 不受影响
- [ ] 代码路径和文档都 **没有** 企业微信、公众号作为入口
- [ ] 凭证不进 git
- [ ] Core 测试不依赖微信适配器进程存活
