## 0. 两截怎么拆

| | P2-A 最小记忆（硬门） | P2-B 记忆补强（非阻塞） |
| --- | --- | --- |
| 挡住谁 | **挡住 P3** | 不挡 P3/P4/P5；建议 P6 前做完 |
| 必须有 | SQLite 事实、称呼/关系、「记住/忘掉」、简单管理页 | episodes、向量检索、风格表、导入脚本、完整 pending |
| 为什么拆 | 语音一旦接上，重启后仍应记得你；不必为了向量库推迟听见她 | 完整中枢工作量大，不该卡在「能说话」之前 |

执行顺序里的「做完 P2 再 P3」**只指 P2-A**。P2-B 可在 P3–P5 之间穿插，只要不破坏 P2-A 的表结构。

---

## 1. P2-A 要做成什么样

新开一个浏览器会话、甚至重启后端，她仍然知道你的称呼和关系。你能在本机页面上看见、改掉、忘掉某条事实。

先做「记得住」，不做「自动变成完美日记」，也不接 QQ。

### 1.1 P2-A 要做

- SQLite 核心事实表（每次对话全量注入）
- 「记住：」「忘掉：」自然语言指令
- 本机简单「记忆」页：列表、编辑、删除（P2-A 可以不做复杂 pending 勾选）
- 消费 `[[natsume]]` 尾块里的 `memory_candidates`：仅自动写入低风险项；其余可忽略或仅日志
- 启动时预置默认称呼「你」、关系「与四季夏目」

### 1.2 P2-A 明确不做（放到 P2-B）

- 向量库、情节摘要检索
- 群导出导入脚本（可预研，不合入为验收项）
- 完整待确认工作流（关系/忌讳自动进 pending 再勾选）——P2-A 对这些 key **只允许用户明确指令写入**
- QQ / 微信在线拉群
- 微调 / LoRA

## 2. 记忆三层（P2-A 只强制第一层）

| 层 | 表 / 集合 | 注入方式 | 谁能写 | 何时落地 |
| --- | --- | --- | --- | --- |
| profile | `facts` 中 `scope=profile` | 每次对话全量 | 你确认，或明确指令；低风险可自动 | **P2-A** |
| episodes | `episodes` + 向量 | 按当前用户句检索 3–8 条 | 会话结束摘要；可待确认 | P2-B |
| style | `style_terms` | 最多 N 条（默认 8）已确认项 | 导入 / 日后 P6；必须人工确认 | P2-B |

Prompt 里必须标明来源，避免模型把记忆当成「刚刚发生的对话」。

---

## 3. 数据模型

文件：`data/memory.sqlite`（不入库）  
向量：`data/vectors/`（Chroma 或 LanceDB，二选一写进 config）—— **P2-B 才建**

### 3.1 `facts`（P2-A）

| 列 | 说明 |
| --- | --- |
| id | PK |
| key | 如 `user.display_name`、`user.nickname_from_her`、`relationship`、`timezone`、`rule.*`、`prefers.*`、`dislikes.*` |
| value | 文本 |
| category | `identity` / `relationship` / `rule` / `preference` / `other` |
| status | `active` / `pending` / `archived` |
| source | `user_cmd` / `extract` / `manual` / `group_import` |
| evidence | 原话摘录，可空 |
| created_at / updated_at | |

**P2-A 启动时必须支持这些 key：**

- `user.display_name`
- `user.nickname_from_her`（默认：你）
- `relationship`（默认：与四季夏目）
- `created_together_at`
- `rules`（可用多行 `rule.<slug>`）

`status=pending` 列 P2-A 可以有、但管理页可以先只展示 `active`。P2-B 再把 pending 做成主路径。

### 3.2 `episodes` / `style_terms` / 独立候选表（P2-B）

规格仍按原设计（summary、embedding_id、term/meaning/usage、`memory_candidates` 队列），此处不提前建表以免和 P2-A 打架。细节见下文 §7。

## 4. 写入规则

| 触发 | P2-A 行为 | P2-B 补充 |
| --- | --- | --- |
| 用户说「记住：我讨厌被催」 | 直接写 `dislikes.rushed`，`status=active`，`source=user_cmd` | 同 |
| 用户说「我叫李雷，你叫我雷雷」 | 写 display_name 与 nickname | 关系若未设，可生成 pending |
| 用户说「忘掉 xxx」 | 模糊匹配 key/value，归档或删除，回复确认 | 同 |
| 模型抽取到「他明天要出差」 | **不写盘**（或只打日志） | 进 pending episode |
| 关系、忌讳、重要承诺 | 无明确指令则不写 | 一律 pending，管理页勾选后才 active |
| 群导入 | 无 | 全部 pending / candidate |

**禁止自动覆盖**已有 `relationship`、`rule.*`，除非用户明确说改。

尾块 JSON（P1 已规定，P2 开始消费 `memory_candidates`）：

```json
{
  "emotion": "happy",
  "silent": false,
  "memory_candidates": [
    { "layer": "profile", "key": "prefers.tea", "value": "喝茶不喝咖啡", "confidence": 0.8 }
  ]
}
```

不要再发明第二套 `[[emotion:]]` 协议。解析失败降级见总纲 §4.2：坏 JSON **不得写入任何记忆**。

## 5. 检索与拼装

Agent system 顺序（相对 P1 插入）：

1. 人设
2. **全部 active profile 事实**（格式：`- key: value`）—— P2-A
3. **最多 8 条 confirmed style** —— P2-B
4. **检索到的 episodes**（标注「长期记忆，不是当前对话」）—— P2-B
5. 通道规则
6. 最近 N 轮
7. 当前句

P2-A 的 `retrieve(query)` 可以返回空列表，但函数要在。P2-B 用当前用户文本（及最近两轮）查向量，过滤 `status=active`。

P2-B 会话结束：页面关闭或空闲超过阈值，或「手动点生成摘要」。最低实现：`POST /api/memory/summarize-session`。

## 6. 接口

全部仅 `127.0.0.1`。

### 6.1 P2-A

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/memory` | 简单管理页（列表/改/删） |
| GET | `/api/memory/facts` | 列表，可按 status 过滤 |
| POST | `/api/memory/facts` | 手建 |
| PATCH | `/api/memory/facts/{id}` | 改 value |
| DELETE | `/api/memory/facts/{id}` | 删除 |
| POST | `/api/memory/forget` | body: `{ "query": "忘掉催我" }` |

聊天路径仍是 `/ws/chat`。Agent 每轮读 MemoryStore，不经前端塞记忆。

### 6.2 P2-B 追加

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| PATCH | `/api/memory/facts/{id}` | 增加「确认 pending」 |
| GET | `/api/memory/episodes` | |
| GET | `/api/memory/style` | |
| POST | `/api/memory/style/{id}/confirm` | 黑话转正 |
| POST | `/api/memory/summarize-session` | 摘要当前 Web 会话 |

## 7. P2-B 规格（不挡 P3）

把原先「完整记忆中枢」的剩余部分放这里。

### 7.1 episodes

| 列 | 说明 |
| --- | --- |
| id | PK |
| summary | 一两句 |
| happened_at | |
| source_chat_id | 如 `web:local` |
| status | `active` / `pending` |
| embedding_id | 指向向量库 |

### 7.2 style_terms

| 列 | 说明 |
| --- | --- |
| id | PK |
| term | 词或梗 |
| meaning | 含义 |
| usage | 她该怎么用 |
| status | `candidate` / `confirmed` / `rejected` |
| evidence | |
| count | 出现次数 |

### 7.3 离线群导入

`scripts/ingest_group_export.py`

- 输入：你从**自己的群**导出的 txt/json（路径通过参数传入，文件放 `data/imports/`，gitignore）
- 清洗：去系统提示、入群消息、明显广告
- 抽候选：调 LLM 输出 facts / style_terms / episodes，**全部 pending**
- 不把其他人隐私（手机号、住址、证件）写入；正则丢掉数字串过长的内容
- 不自动 confirmed
- **不发起任何网络到 QQ**

用一份脱敏样例跑通即可，不要求真群。P6 之前这只是预研/补强，不是 QQ 通道。

## 8. 实现顺序

**P2-A（必须先验收）：**

1. `schema.sql` 的 `facts` + SQLite `MemoryStore`
2. Agent 注入 profile_block（先手写两条事实验证）
3. 「记住 / 忘掉」指令解析
4. `/memory` 简单页
5. 按第 9.1 节验收 → **可以开工 P3**

**P2-B（之后任意穿插）：**

6. 候选 JSON + pending 工作流
7. episodes + 向量检索
8. style 表 + 导入脚本
9. 按第 9.2 节验收（建议 P6 前完成）

## 9. 验收

### 9.1 P2-A（硬门）

- [ ] 说「我叫 X，你叫我 Y」，重启后端再开页面，她仍正确称呼
- [ ] `relationship` 可在管理页改、删，下一轮对话立刻生效
- [ ] 「记住：我讨厌被催」写入 facts 且可在管理页看见
- [ ] 「忘掉被催」后她不再主动用这条
- [ ] 进程重启 sqlite 文件还在
- [ ] 坏 `[[natsume]]` JSON 不写记忆（单测）
- [ ] 仍无 QQ/微信登录代码
- [ ] 仍无向量库依赖进入 P3 必装清单

### 9.2 P2-B（补强）

- [ ] pending 条目未确认前不进 prompt
- [ ] 导入脚本对样例文件只产生 pending/candidate，不发 QQ
- [ ] 情节检索能把相关旧摘要注入，且标注「不是当前对话」

## 10. 交给 P3 的接口

语音通道必须复用同一个 `MemoryStore` 与同一个 `chat` Agent。  
P3 新增输入方式时，**profile 全局共享**；P2-B 的 episodes 可带 `source_chat_id`，检索默认跨通道（自用，你就是你）。
